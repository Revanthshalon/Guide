# Decorator (Wrapper) — Quick Reference

## One-Liner

The Decorator pattern attaches new behaviors (logging, caching, retries) to an object dynamically by placing it inside wrapper objects that implement the exact same interface.

## When to Use / When Not

| Use it when | Avoid it when |
| --- | --- |
| Adding orthogonal behaviors to a core component without modifying it | The trait has dozens of methods and you only need to decorate one (boilerplate heavy) |
| Stacking multiple configurable behaviors (middleware) | You need to alter the interface (use Adapter) |
| Building I/O pipelines or network services | The execution order of concerns is highly intertwined and impossible to separate cleanly |

## Structure Sketch

```rust
// 1. The Trait
pub trait Component { fn execute(&self); }

// 2. The Core Implementer
pub struct Core;
impl Component for Core { fn execute(&self) {} }

// 3. The Decorator
pub struct Decorator<T> { inner: T }
impl<T: Component> Component for Decorator<T> {
    fn execute(&self) {
        println!("Before execution (e.g., Metrics Start)");
        self.inner.execute();
        println!("After execution (e.g., Metrics End)");
    }
}
```

## Rust Idiom

- **Generics over Trait Objects:** The standard idiom is `struct Wrapper<T> { inner: T }`. This achieves zero-cost static dispatch.
- **Tower Ecosystem:** `tower::Service` and `tower::Layer` are the pinnacle of the decorator pattern in Rust async networking.
- **`impl Trait`:** Use this at API boundaries to hide the massive `Outer<Inner<Core>>` type signatures generated by stacked decorators.

## Versus

| Confused with | Key difference |
| --- | --- |
| **Proxy** | Controls access/lifecycle (lazy init, security). Decorator injects orthogonal behavior. |
| **Adapter** | Converts an interface to make it compatible. Decorator keeps the exact same interface. |
| **Chain of Responsibility** | Handlers can break the chain and return early. Decorators generally wrap and delegate down to the core. |

## Pitfalls → Mitigations

| Pitfall | Mitigation | Watch out for |
| --- | --- | --- |
| **Type Explosion** | Hide the stacked types behind `impl Trait` or `Box<dyn Trait>` at boundaries. | Compiler errors exposing `A<B<C<D>>>`. |
| **Execution Order Errors** | Explicitly map out the onion. Outer layers wrap inner layers. Telemetry on the outside. | Cache decorators placed outside telemetry decorators. |
| **Delegation Boilerplate** | Segregate large traits into smaller ones so decorators only implement what they care about. | Implementing 20 pass-through methods manually. |

## Rules of Thumb

- A Decorator **must** implement the same trait as the object it wraps.
- Decorators should be infinitely stackable.
- Put observation (metrics, tracing) on the absolute outside. Put mutation (auth injection, headers) on the inside.
- Default to generics for performance; use trait objects only if the decorator stack must be reconfigured dynamically at runtime.
